## 1. `JCP1704U` — the plastic master is sorted twice

`S020SORT` and `S090SORT` both read the **same** input, `&ENV.CIS.BTHVSM.&VER.CPBPLT`,
and both sort on the **same key**:

```
 SORT FIELDS=(20,2,PD,A,288,9,PD,A)
```

They differ only in the `INCLUDE`:

| Step | `INCLUDE COND` | Output |
| --- | --- | --- |
| `S020SORT` | ORG `001` or `201`, and `22,2,PD NE 998` | `EIS.CPBPLT` |
| `S090SORT` | ORG `005`, and `22,2,PD NE 998` | `EIS.CPBPLT.ORG005` |

So the job makes **two complete passes over the plastic master to produce two mutually
exclusive subsets**, and pays the sort twice. One DFSORT pass with two `OUTFIL FNAMES=`
produces both — the key is identical, so the records and their order in each output are
unchanged. This is pattern **P3** in [`../jcl/PATTERNS.jcl`](../jcl/PATTERNS.jcl) applied
to the largest daily job outside the A7 plans.

Both steps already point `SORTCNTL` at `ICPK0250`, so the tuning is there; it is the
second read of `CPBPLT` that is waste.

### The join step is the untuned one

`STEP040A` runs a DFSORT `JOINKEYS` across two VSAM masters —
`RDM.CUSPLT` and `CPBCRD` — with a 22-field `REFORMAT` and a 3,000-cylinder output. It
is almost certainly the most expensive single step in the job, and it has:

- **no `SORTCNTL` or `DFSPARM`** — unlike `S020SORT` (`ICPK0250`), `S040SORT`
  (`ICPK0100`) and `S090SORT` (`ICPK0250`);
- **no `AMP` buffers on `SORTJNF1` or `SORTJNF2`**, though both are KSDS read end to end.

### The VSAM reload has no buffers either

`STEP040B` defines `RDM.CUSPLT.CCRIS` at `CYLINDERS(3000 200)` — correctly, with
`SPEED` — and `STEP040C` then loads it with a bare `REPRO`:

```jcl
//INDD1    DD  DSN=&ENV.CRD.BTHSEQ.&VER.RDM.CUSPLT.CCRIS,DISP=SHR
//OUTDD1   DD  DSN=&ENV.CRD.BTHVSM.&VER.RDM.CUSPLT.CCRIS,DISP=SHR
```

No `AMP` on either DD, for a 3,000-cylinder load. The same job tunes buffers carefully
everywhere else — `CUSPLT` reads with `AMP=('BUFND=91','BUFNI=138')`, `CPPLTS` with
`DCB=BUFNO=31` — so this is an omission, not a policy.

### `CP608250` runs twice over the same masters

`S060EIS` and `S100EIS` execute the same program with near-identical DD lists: nine VSAM
files (`CPBCUS`, `CPBSYS`, `CPBKYC`, `KCMACC`, `KCXUPL`, `CUSPLT`, `CPNACCV`, `BNMCC`,
`EISCC`, `CPBASF`) opened, read and closed twice per night. The only differences are the
`CPPLTS` subset and the output DSNs.

Whether the two can merge depends on `CP608250`'s logic and its `PARMIN` member
`ICP01409` — that is an application-owner question, not a JCL one. Flagging it because
it is the largest remaining structural cost in the job once the double sort is fixed.

### `EISWKLY` has grown seven times; its allocation has not been revisited

The revision trail records `LRECL` going 1827 → 2000 → 2500 → 3900 → 4200 → 4500 → 5000
between 2018 and 2025, each change commented out above the live `DCB`. `SPACE` has
stayed `(&PRM,(3500,900),RLSE)` throughout. Worth a look at actual extent use — a record
that has grown 2.7× on an unchanged primary allocation is how secondary-extent thrash
starts.

## 2. `JCP2513U` — a duplicate step name, and eight unbuffered VSAM loads

### The defect: `CSSUBS1C` is coded twice

The job rebuilds eight files in near-identical blocks. The `CSSUBST` step in each block
is named for its block — `CSSUBS1C`, `CSSUBS1D`, `CSSUBS1E`, `CSSUBS1F`, `CSSUBS1G` —
and then the merchant-posted block at the end of the job reuses **`CSSUBS1C`**:

| Step name | Block | Control members |
| --- | --- | --- |
| `CSSUBS1C` | History transaction file 1 | `QMDLH01N` / `QMDFH01N` |
| `CSSUBS1D` | History transaction file 2 | `QMDLH02N` / `QMDFH02N` |
| `CSSUBS1E` | History transaction file 3 | `QMDLH03N` / `QMDFH03N` |
| `CSSUBS1F` | History transaction file 4 | `QMDLH04N` / `QMDFH04N` |
| `CSSUBS1G` | History transaction file 5 | `QMDLH05N` / `QMDFH05N` |
| **`CSSUBS1C`** | **Merchant posted file** | `QMDLMPTN` / `QMDFMPTN` |

The sequence runs C, D, E, F, G and then returns to C — the signature of the merchant
block having been cloned from the history-file-1 block, with the `IDCAMS` steps renamed
to `QMTMPT0n` and the `CSSUBST` step missed.

This is not a performance item. A duplicate step name makes step-level `COND=` references
bind to the first occurrence, and makes restart-at-step ambiguous — so an operator
restarting this job at `CSSUBS1C` after an abend in the merchant block may silently
re-run the history-file-1 rebuild instead. Rename the second one (`CSSUBS1H` keeps the
sequence) and check whether any OPC restart instruction or QRG names it.

### Eight bulk VSAM loads, none buffered

The job's shape is eight repetitions of: sort a `QMU007.QMHSTnn` sequential file, delete
and define a fresh KSDS, `REPRO` a dummy header record, then `REPRO` the sorted data in.
That is **16 `IDCAMS REPRO` steps, and not one of them carries an `AMP` buffer
specification** — `IDCAMS3A`/`3B`/`3C`/`3D`/`3E`/`3F`/`3G` and `QMTMPT04` are the bulk
loads, each fed by a sort output allocated at 1,000–3,000 cylinders.

Buffering the `OUTDD1` of those eight loads is the single largest lever in this job, and
it is a DD-level change with no logic impact. Also confirm the `QMDFH0nN` / `QMDFMPTN`
define members specify `SPEED` rather than `RECOVERY` — `JCP1704U`'s equivalent define
does, so the convention exists.

### Sort tuning is inconsistent, and backwards

| Steps | Parm member | Gives |
| --- | --- | --- |
| `SORT1A`, `SORT1B`, `REMDUP`, `MERGE2` | `ICPK5000` via `DFSPARM` | `FILSZ=E5000000` + `DYNALLOC=(DISK,32)` |
| `SORT1C`–`SORT1G`, `QMTMPT01` | `DYNALL32` via `SORTCNTL` | work count only, **no size estimate** |

The six steps with no size estimate are the ones sorting the history files, allocated at
1,000–3,000 cylinders each. The four that do have an estimate are the smaller cross-
reference sorts. Give the history sorts the matching `ICPK` member.

### Four temporary datasets are routed to virtual tape

`&&QMHSXP`, `&&QMHSXS`, `&&QMHDUP` and `&&QMHSXSM` are `&&`-prefixed temporaries —
written and read back inside this one job — yet allocated `UNIT=VTAPE1`. Their siblings
`&&QMHNDUP` and all six `&&QMHSTnn` go to `UNIT=DISK`. Same inconsistency as the
`CLRNP02` chain in [`10_longpole_findings.md`](10_longpole_findings.md), and the same
DASD capacity question applies.

### 45 steps against a 20-step shop limit

Counting named steps: 45, before the `CSSUBST` PROC invocations expand. The estate's own
JCL standard limits a job or proc to 20 steps. Any restructuring should split the eight
rebuild blocks out — which is also the parallelism opportunity below.

### The eight blocks are independent

Each block sorts its own input and loads its own output cluster; nothing flows between
them. They are the cleanest partitioning candidate found so far — structural rather than
key-range, so pattern **P6**'s "no cross-account state" caveat does not bite.

One caution from the job's own header:

```
//* *** IMPORTANT : THERE MUST ALWAYS BE ONE EXTRA FILE AVAILABLE TO
//*     FACILITATE THE HISTORY TRANSACTION BUILD PROCESS.
```

There is a file-rotation rule around the history set, so the split needs the acquirer
module owner's confirmation before any OPC work. And at 70 minutes **once a month**, this
is worth far less than it looks — do `JCP1704U` first.
